# HealthOps Intake Agent V3

## 使用方式

会员 → Member360 → 健康档案：上传资料 → 看助手整理 → 处理剩余例外 → 一次确认提交初评资料。
10 张分类卡片和原有 11 步页面继续用于查看、修正及高级编辑。完成资料提交后，原有健管专业确认、医生核对流程保持不变。

## 实现边界

- 复用 `LocalLLMClient.generate_structured`、现有 Provider 配置及不可用回退；没有新增模型配置、客户端或 Agent。
- 继续使用现有 PROFILE_INTAKE、解析候选、AssessmentImportService 和 ManagementWorkflowService。
- 确定性规则与结构化映射优先；仅未处理的自由文本交给现有本地模型。
- 压缩提取提示中的结构说明，避免完整 JSON Schema 占满现有输入预算、挤掉原文。
- 每个可采用的候选必须逐字核对原文；文档、位置、日期、置信度和待确认状态由服务绑定。没有原文依据的结果被拒绝并保留人工核对提醒。
- 知识库不参与会员事实提取。界面显示“本流程未使用”，不生成检索成功事件。
- 可靠规则结果保留为待总确认的草稿建议；语义结果逐条确认，冲突必须明确处理。新增来源使旧确认失效。
- 未填写的可选字段保持未知；必需回答进入问题队列。明确记录“不清楚”不同于记录“无”。
- 最终调用原有初评提交服务，不要求遍历 11 步。正式用药仍须医生确认，不新增推断诊断。
- 报告测量通过既有候选确认服务入档；继续执行原有标准指标、单位、日期、重复及风险规则，不修改 Risk Engine。
- 18px 医疗蓝圆环仅由 RUNNING 或真实请求回调驱动；人工等待、完成及失败时不旋转；尊重减少动态效果设置。

健管输入“七小时”和“改善午后精力”；确认两项语义候选、按有日期的来源处理吸烟状态冲突，并核对报告测量。没有进入 11 步目录，一次提交后原有三个资料处理实例均完成。

本机 7B 模型耗时存在明显波动：首次实际请求约 438 秒，第二次约 298 秒，最终完整复跑为 5.13 秒；等待期间一直显示真实请求状态。不能把最后一次结果解读为稳定的响应时间保证，调用记录见验收数据的 `llm_activity.latency_ms`。

浏览器发现并修复了一个持久化问题：Member360 传入的是已脱离读取会话的初评对象，上传时必须重新读取当前会话中归属正确的记录再保存流程标记。已有多文件草稿也可直接使用例外队列，不要求重新上传。

准备度统计采用现有字段定义：基础资料、各历史表一条记录、生活方式、环境、关注问题合计 57 个字段；表格新增记录按实际字段增加分母。自动整理、待确认、冲突是同一批来源字段的不同状态，不相加当作健康评分。

提交表示问卷资料提交完成，并不替代原有健管专业确认或医生医学判断。
