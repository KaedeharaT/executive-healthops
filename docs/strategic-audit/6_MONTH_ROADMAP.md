# HealthOps：按长期资产安排的六个月路线

基线：2026-10-04，HEAD `bf1b0558425480b9209d9867b046f24c25134dfd`。时间窗为未来六个月，按月度里程碑表达，不代表已经批准上线或已完成实现。本轮只审计。

**投资目标：让平台每管理一个人、经历一次人工纠正、完成一次干预，都留下以后仍可使用的可信经验。** 成功不是模型数量或Agent数量增长，而是新健管能接续管理，Agent下次知道哪些安排不适合这个人，以及每次结论能回到事实和责任人。

## 三项投资，按依赖推进

| 投资 | 要积累的资产 | 不以什么作为完成标准 |
|---|---|---|
| 1. Care Memory | 有证据、时间范围、确认/推断状态、修正及失效关系的管理经验 | 不以新增Memory类、embedding或一段LLM总结为完成 |
| 2. Intervention → Outcome | 建议、人类决定、执行事实、结果窗口、会员反馈及原因的同链关系 | 不以任务状态COMPLETED或一个改善百分比为完成 |
| 3. Goal-driven Context | 不依赖模型/设备的目标、指标、有效事实与相关记忆上下文合同 | 不以多Agent或更长prompt为完成 |

三个方向对应 [GAP_MATRIX.md](GAP_MATRIX.md) 的G01/G02/G03；其他P1工作为它们提供可信基础，不另开十个同等优先项目。

## 第1–2月：把服务历史变成可治理的照护记忆

**主要资产：可信事实、目标语义、来源清楚的Care Memory。**

先选一个有限目标和一种实际可交付的管理场景，例如睡眠执行障碍或体重管理跟进。选择依据是业务团队确实能连续记录与随访，而不是设备品牌数量。不能把演示阈值直接带入真实健康规则。

优先工作：

1. 做事实来源/版本覆盖盘点，区分已知、缺失、无法恢复；确认正式使用哪个数据库和schema。只通过独立、可回滚迁移任务解决默认库0031/正式Demo0032差异，不重建数据。
2. 在现有Metric/Goal Registry补足所选场景的时间与版本合同：点值/区间/累计、单位、来源、确认时的指标要求。所有消费者遵守确认版本，避免历史口径漂移。
3. 定义三种分开的内容：正式健康事实、当前Goal工作状态、长期管理经验。记忆条目必须链接原始日志/反馈/医生记录、时间范围、确认/推断、更新/失效状态；模型不能把推断永久提升为事实。
4. 先把现有ExecutionBarrier、WeeklyReview、ManagementLog利用起来。记忆候选描述“在什么背景下尝试什么、执行如何、依据何在”，不把相关性称为疗效。
5. 定义统一Context Assembly输入/输出合同和相关性规则，先接一条随访流程；禁止全量人生历史进入模型。

建议责任：数据/后端负责人负责版本和引用；健管业务负责人定义“有效管理记忆”；医生审核医学表达边界；产品负责人确保仍在原有管理/历程内呈现。

验收标准（建议目标，不是现状数据）：

- 同一合成会员连续两次干预未执行，原因“夜班”，后来本人更正原因；可以逐次重建原文、作者、发生时间和修正，旧推断不再作当前事实。
- 下一次随访能读取相关经验，并显示引用；无关检验不进入睡眠上下文。
- 选定试点的新记忆100%有可解析source refs/time range/status；无法确认者明确inferred，不能自动成为诊断或医生意见。
- 目标/指标版本变化不会改变已确认历史目标的原始要求；缺数据不填造数值。

本阶段不做：全病种Memory大一统、全量历史自动LLM总结、知识图谱重构、换模型、换Agent框架。

## 第3–4月：让每次行动有可追溯的执行与结果

**主要资产：个人干预历史、人/医生的决定、会员反馈和结果。**

优先工作：

1. 复用现有Task、RecheckPlan、ServiceRequest及ManagementLog，补共同管理尝试身份与关系。明确建议版本→谁接受/改了什么/拒绝原因→执行对象→完成/未执行/中断→结果测量与反馈窗口。
2. 不混淆“服务完成”和“健康改善”。Outcome允许无效、无明显变化、数据不足、未执行和拒绝；原因及证据缺失都要明确。时间前后比较只能描述观察到的变化。
3. 将会员本人纳入小问题闭环：执行了没有、遇到什么困难、是否愿意继续。本人提交与健管代录分别标来源，绑定原问题/Goal，完成后恢复原事项。
4. 在已存在DoctorReview/ClinicalRecommendation上补责任与行动关联，覆盖旧阶段医生流程，保留医生签署来源；不能仅因原文出现“医生”就变为医生结论。
5. 修正所选场景的日摘要时间语义、缺天持续性、迟到/纠错重算、事件证据修订和真实规则覆盖。复用既有Risk/Management规则审核，不发明医学阈值。
6. 统计Human Gate为什么出现、是否修改、重复确认次数和耗时。只在已有批准、可逆低风险范围减少无意义复核；目标、计划、医学、高责任阶段仍保留人的责任。

建议责任：业务负责人定义行动/结果口径；数据工程负责人保证关系可查询；医生负责医学决定与规则审批；产品负责人负责会员反馈和既有工作台小问题。

验收标准：

- 能从一次Outcome反向定位建议版本、健管修改、医生依据、实际执行及相应Observation/会员反馈；无法归因处显示“关联不明”，不硬连。
- 所选试点新行动建议至少95%能关联到人类决定及执行对象；100%医学行动具明确医生依据。这是预设验收目标，需先建立分母和责任定义。
- 稳定连续数据在有实际适用规则时无无意义Agent唤醒；变化仅一次逻辑事件，来源修正能更新/替代证据而不重复建立任务。
- 同一Goal等待会员/医生，重启后正确恢复；不关联的旧结果不能关闭新RED。
- 阶段复盘后生成有证据的经验更新；下阶段能够使用它，解决现有StageReview→Memory断点。

本阶段不做：自动治疗建议、从前后对比直接学习医学因果、用医生意见直接训练上线规则、为“统一”另建第二套服务/任务表。

## 第5–6月：证明长期经验确实改善下一次管理

**主要资产：可复用个人响应模式、可审计的决策上下文、版本化知识使用证据。**

优先工作：

1. 将统一Context Assembly用于报告变化、日Summary变化、随访与阶段复盘。读当前Goal/有效事实/相关历史/记忆/医生意见/开放行动，并记录本次选择与排除依据。
2. 在受控工具与固定责任关卡内引入有限重规划：因会员明确拒绝、工作班次变化、既往执行失败而调整运营安排；不追求L4自由Agent。
3. 复用已有知识审核、有效期、范围和citation。每项引用记录当时版本，关联人类修改与最终决定；统一两个知识工具合同。更换检索引擎只是可选实现，不是目标。
4. 开展同一会员跨月“盲重建”：新健管只看持久记录，能解释目标为何变、过去哪次尝试失败、当前等谁以及下一步。用缺链率而不是模型文案流畅度评分。
5. 用第二个模型或同类设备做边界验证：事实ID、版本、责任和结果链不改变，关键确定性结果一致。若一个Adapter要求重写Agent，优先修语义边界，而不是继续扩厂家数。

建议责任：临床/健管业务负责人评审重建正确性；Agent负责人验证上下文与受控规划；质量负责人维护长周期故事和边界回归；知识负责人确认引用适用性。

验收标准：

- 在相同会员、相同当前事件下，加入已确认失败历史时，下一步安排能合理改变并引用证据；加入无关、过期或被纠正的记忆时不被误导。
- 多月故事可从持久数据重建，无需LLM补事实；明确标识MISSING LINK/MISSING DATA MODEL，缺失率持续下降。
- 所选闭环新决策引用的事实/记忆/知识版本均可恢复；换模型不改变医学责任门槛、Raw/Confirmed事实与风险规则。
- 人工介入次数和耗时相对试点基线下降，同时错误接受/遗漏必要医生Gate不增加。达标阈值由试点基线和业务质量标准共同确定，不能先虚构“改善率”。
- 开始形成按个人的“哪些运营安排可执行、哪些背景需调整”的经验；仍不把小样本相关性宣传成临床效果。

## 六个月全程看哪些数字

| 指标 | 分母/定义 | 用途 |
|---|---|---|
| 可追溯事实比例 | 新正式事实中，有原始依据、发生时间、治理状态、当前版本关系的比例 | 检验Data Model资产质量 |
| 可用记忆比例 | 有来源/时段/状态且未失效的记忆占全部当前记忆比例 | 防无来源总结堆积 |
| 记忆使用正确率 | 后续决策中使用记忆的引用是否相关、有效、归属正确 | 证明不是只“存过Memory” |
| 决策—执行关联率 | 有人类决定及执行对象引用的新行动建议比例 | 检验闭环关系，不以任务数量代替 |
| Outcome证据覆盖 | 评价到期且有执行事实、测量/反馈依据的行动；未执行/缺数据单列 | 防选择性只报成功结果 |
| 小问题人工负担 | 每次业务闭环Gate数、耗时、无修改确认比例、必要责任遗漏 | 同时避免伪HITL和过度自动化 |
| 历史重建缺链率 | 预定义故事问题中标MISSING LINK/MISSING DATA MODEL的比例 | 直接衡量长期数据库是否成为可用记忆 |
| 摘要/变化可靠性 | 缺数据、重算、撤销、重复唤醒、错误连续天数的发生率 | 保证连续状态可用于决策 |

这些是过程与证据指标，不是“健康改善率”。真实健康目标进度继续使用已确认目标及实际数值；健康结果需在明确口径和证据范围内评价。

## NOT PRIORITY

| 方向 | 当前为什么不是优先 |
|---|---|
| 换更强模型/接更多模型 | 不能解决日志缺链、历史版本和Care Memory治理；现有provider边界已可替换 |
| 为RAG先建复杂向量平台 | 审核来源/有效期/检索合同已有，关键是引用进入真实决定与结果链 |
| Multi-Agent数量扩张 | 已有持续MemberAgent；需要更完整上下文和责任，不是更多身份 |
| 自由规划L4 Agent | 无助于填补可信证据；当前L1先向有限上下文规划演进即可 |
| 接十个设备厂家 | 先让一个目标的一条连续数据链正确、可修正、可评价 |
| 全面知识图谱或统一万能表 | 现有事实/任务/阶段足够复用，应先修关系和语义治理 |
| 新Goal/Risk/Memory页面、大屏或AI聊天页 | 现有Member360和今日工作已经承载主要操作；保持V7及Soft Neumorphism |
| 自动从医生结论学习治疗/风险规则 | 医学责任及规则生效需要明确治理与人工批准 |
| 用合成Demo数据证明长期效果 | 合成故事用于测试关系和边界，不能替代真实纵向资产 |

## 投资停止条件

如果试点只能产出更多摘要，却不能回答“谁决定、执行了什么、为什么没执行、依据哪个版本、下次如何不同”，应暂停扩展场景，修复G01/G02/G03。不能用新增模型、设备或页面数量掩盖资产没有积累。

本轮只交付审计与路线。未修改业务代码、UI或数据库，未commit，未push。
