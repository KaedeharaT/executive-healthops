# 初评人工工作压缩审计

基线：`e230143baa902f165ff64c1c570c2ab3d356318f`（开始时实际 HEAD）。
本地备份：`backup/pre-intake-human-work-compression`。不修改正式会员数据；真实案例仅以只读连接复算，交互验收使用独立合成数据库。

## 原来的 52 项

从当前数据库找到与问题一致的两份资料初评：

| 旧统计 | 实际值 | 含义 |
|---|---:|---|
| 显示的评估总项数 | 57 | 基础模板槽位；未正确展开多条病史 |
| 自动预填 | 46 | 43 个待确认候选 + 3 个冲突，不能理解为 46 个自动采纳值 |
| 缺失 | 25 | 4 个旧规则必补 + 21 个可选缺失 |
| 人工队列 | 52 | 43 确认 + 3 冲突 + 4 必补 + 2 文件核对 |

**不能把 52 解释成“25 个空字段都被强制补齐”**：旧版已经排除了其中 21 个可选字段。真正的主要原因是：

1. 只要候选来自本地 LLM，旧投影便无条件要求逐项确认，忽略其原文依据和实际歧义程度。
2. 现有提取器对 LLM 结果统一标记 MEDIUM，这不是测得的语义不确定度；旧界面却据此把整批结果都交给人。
3. “自动预填”同时包含待确认和冲突，统计重复；同一份信息看似已经整理，却又全部需要人处理。
4. 必补清单按类别固定，家族疾病、手术名称等在没有对应事实时仍被要求回答。条件字段没有版本化提交策略。
5. 对有明确日期的生活方式变化仍生成冲突。无日期、同日期矛盾、人口学差异及医学事实差异仍应核对。
6. 歧义字段的分组区分了原文位置，但决策键遗漏该位置；不同记录的同名字段可能共用确认键。本轮补齐来源身份。
7. 旧总数只计算模板槽位，候选队列却按多条记录计算；“57 总项”和多条病史的实际明细不在同一口径。

## 正式规则

新增 `IntakeRequirementPolicy(initial-v1)`，不依赖数据库 nullable：

- 必须获得会员称呼、病史/过敏/当前用药的实际回答、睡眠/烟草/饮酒、会员关注问题。允许会员明确回答暂不清楚；不得由空白推导“无”。
- 家族中明确存在某疾病时，患病家属是条件必需信息；报告手术且需要持续随访时，随访内容为必需。
- 明确否认对应历史后，附属细节为 NOT_APPLICABLE，不凭空填日期、医院等信息。
- 环境暴露细项、历史用药细节等可选项允许暂缺，不能阻塞本次提交。
- 低置信度、模糊表达、原文依据不完整、记录归属不明，继续人工确认。未明确归属的字段必须由人指定记录或说明不采用原因。
- 自动整理仅用于初评草稿，保留原文、文件、位置、日期和置信标记。正式健康事实、测量确认、Risk、医生责任仍使用已有服务和边界。
- 不同时间的可变生活方式/环境自述，只有所有来源日期有效、最近日期无歧义且没有现有已确认值冲突，才可自动采用当前状态。旧来源仍保留。
- 文件读取问题及测量候选核对仍是独立来源核对事项，不能为了减少数字删掉。

每个 `(类别, 记录身份, 字段)` 只属于一个当前状态：

```
TOTAL = AUTO_FILLED + NEEDS_CONFIRMATION + CONFLICT
      + REQUIRED_MISSING + OPTIONAL_MISSING + NOT_APPLICABLE

Human work = NEEDS_CONFIRMATION + CONFLICT + REQUIRED_MISSING + DOCTOR_REQUIRED
```

统计中的 TOTAL 为评估工作项：真实记录字段 + 未完成的来源核对单元；`field_total` 单独给出真实字段数，`document_reviews` 明确给出文件核对数。医生判断是独立责任关卡，不伪装成空字段。
AUTO_FILLED 表示当前已有可用于初评的草稿值；`origin` 区分资料、既有回答和人工解决结果。人工确认/补充/冲突处理另外记录，不增加该字段的状态计数。来源核对完成后退出未完成工作项；新增真实记录或来源会重新计算分母，百分比不代表健康评分。

## 原有流程保持

- 界面继续使用 V7 和现有 Soft Neumorphism Token；没有新菜单、新 Agent 或聊天界面。
- RUNNING 使用原 AgentProgressPanel 的真实步骤、当前文件、耗时与 spinner。
- WAITING 停止 spinner，主要动作仅为处理必要例外。规则、AI、知识（本流程未使用）、文件和耗时放入默认折叠的“处理记录与来源”。
- 每项保存调用原服务并自动进入下一项，显示人工队列进度；11 步保留为次级“完整查看 / 手工修正”。
- 最后一次总确认通过原提交服务生成 `INTAKE_ASSESSMENT_CONFIRMED` SYSTEM HealthEvent；同一 MemberAgent 接收事件，继续原 Intake Goals 的收尾。幂等事件和来源关联防止重复执行。确认事件按实际提交时间区分版本；同次确认在进程重载后仍幂等，退回补充后的再次提交可以继续新增资料。
- 后续健管专业初评是既有必要判断，不要求重新填写 11 步；需要医生时继续原医生流程。可识别体检报告仍按已有策略接续体检后管理。
- 无新增外部请求或长计算写事务，无 Risk Engine、Tool Registry、Planner、设备入口、医生判断逻辑修改。
