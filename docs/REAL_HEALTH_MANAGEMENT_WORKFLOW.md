# 会员全周期健康管理实施

## 来源与隐私边界

本轮未收到《健康管理日志》和《病理及生理衰老评估表（M）》原件，工作区也未发现这两份附件。因此只使用用户消息明确提供的业务结构，不声称读过原件或复刻原量表。没有从真实资料提取姓名、诊断、用药、机构、联系方式或报告值。

演示、测试和浏览器操作只使用明确标注Synthetic的合成会员、医生、机构、报告与事项。原医学量表题目与授权版本仍待原件核对；当前允许逐项记录原始问题、回答和0—4分，不计算诊断或虚构量表效度。

## 业务主线

签约入组 → 会员建档 → 初始问卷 → 资料收集 → 健管初评 → 必要检查与医学确认 → 年度基线 → 年度方案与任意数量阶段 → 管理日志与事项 → 检查复查 / 医疗协同 / 服务执行 → 阶段评估 → 下一阶段 / 下一年度。

原产品的健康状态、健康运营、长期记录仍存在；数据、规则风险、任务与自动化服务于会员周期，支撑配置保留在管理员。

## 事实归属与模型复用

|业务|事实模型 / 表|实施边界|
|---|---|---|
|会员基础档案|Patient / patients|问卷基础步骤直接编辑原档案，不复制姓名、生日和性别；身高体重仍用Observation|
|周期、年度目标|HealthProgram / health_programs；AnnualHealthAccount|复用原模型，新增cycle_year、客户顾问；开始结束日期与owner沿用原字段|
|任意数量阶段|ProgramPhase / program_phases|补管理内容、负责人、实际完成时间、结果反馈；保留原阶段服务与历史计划|
|初始自述与健管初评|IntakeAssessment / intake_assessments|按会员、年度唯一；分步骤JSON有字段白名单，基础档案只保存已核对标记；会员关注与专业重点独立|
|日常管理日志|ManagementLog / management_logs|原FollowUp要求健康问题且缺沟通、周期、机构与多来源关联；ServiceEvent过于简略，因此新增最小日志表|
|复查协调|RecheckPlan / recheck_plans|原任务没有预约→执行→报告→复核过程，新增协调状态；报告、观测和依据仍引用既有记录|
|正式会诊|ConsultationCase / consultation_cases|只存申请、参与者、汇总结论与行动草稿；Encounter与ClinicalRecommendation继续承载医疗记录和逐科意见|
|服务执行|ServiceRequest / service_requests|只补周期、阶段和管理任务关联；申请、审核、安排、开始、结果沿用原Service服务|
|阶段执行评估|StageReview / stage_reviews|原WeeklyReview按周、OutcomeEvaluation按数值，均不能表达整阶段执行核对；新增阶段复盘，数值比较仍沿用OutcomeEvaluation|
|家庭关系|FamilyRelation / family_relations|家属关系、可选关联会员、联系人与紧急标记；不建立家庭登录，不自动授权共享权益，不代替风险应急联系流程|
|正式用药|MedicationPlan|问卷候选不会自动入档；医生核对正式来源后才可确认映射，重复确认幂等|

## 状态与人工关口

- 入组状态由事实投影：待建档、资料收集中、待健管初评、待补充检查、待医学确认、待建立基线、待制定方案、持续管理中。
- 问卷：草稿 → 已提交 → 已确认；支持健管退回补充。症状原始分数无诊断、无正式Risk副作用。
- 初评：DRAFT → READY_FOR_REVIEW → WAITING_MEDICAL_REVIEW（需要时）→ CONFIRMED。检查建议/医学问题由现有DoctorReview承接。
- 年度方案启动需要本年度确认基线、确认初评和至少一个阶段；阶段日期在服务周期内，不能交叠。
- 复查：待确认 → 待预约 → 已预约 → 待执行 → 已完成 → 待报告 → 待复核 → 已关闭；转复核需要报告，关闭需要人工结果。
- 会诊：待准备 → 待举行 → 待整理结果 → 待方案拆解 → 已完成。每位参加医生提交本人科室意见，收齐后由医生确认综合结论，健管保存草稿不会生成任务，明确确认才创建事项。
- 阶段复盘记录实际完成、数值变化、用药/检查/生活方式/服务执行、未解决问题、下一阶段建议。进入下一阶段必须已有下一阶段；医学复核决定调用原DoctorReview对象，不制造临床判断。

## 写入与投影

`ManagementWorkflowService`是新增UI/API共用命令层，事务由调用者提交。`MemberManagementProjection`是只读会员工作上下文；`OperationalWorklistService`加入初评、到期复查、会诊待拆解和到期阶段复盘，未新建管理事项事实表。

日志保存与关联随访Task在同一事务完成；请求键防止同次提交重复。完成医生复核后，已入组会员另有立即接收结果的健管交接待办，原建议日期的随访任务仍保留。复查与阶段到期由队列读取时按时间投影，无需新增Agent；不承诺离线推送或后台短信。

所有新增写入保留AuditLog，关联记录校验会员归属。UI不直接拼写ORM。管理API为 `GET /management/members/{id}` 和 `POST /management/members/{id}/commands`，action白名单覆盖入组、问卷、初评、阶段、日志、复查、会诊、方案、服务关联与家庭关系。

现有系统仍是演示身份切换；API声明的角色不是真实登录凭证。新增医生角色关口用于流程边界，不宣称完成生产认证或真实PHI试点安全。

## 工作人员入口

- 今日工作：统一短队列＋选中详情；事项来源筛选，前往同一会员上下文处理。
- 会员：新建档案及会员360；概览 / 健康档案 / 管理 / 医疗 / 历程。
- 年度管理：服务周期、目标、阶段、下一节点、责任人；可入组与进入会员管理。
- 医疗协同：原医生复核、正式会诊、原外部医疗均保留。
- 服务：原审核、安排、执行、证据、结果与后续；会员管理中关联周期、阶段、事项。

管理日志在会员360管理默认展示；原计划、任务、随访、数值阶段结果和自动跟进入口归入“原有计划 / 任务 / 自动跟进”。初始问卷在健康档案，也会在未提交成员首页显示“完善健康档案”；提交后首页不再占用该入口。

## 长期记录

普通电话、提醒和日常管理日志不加入成员主时间轴。确认后的会诊判断、阶段结果投影到原HealthTimelineService；不新增第二事实表，不用Agent Trace代替长期记录。原报告、基线、风险、用药、医生、服务与Outcome图表/历程保持。

## 数据库与演示

迁移 `0027_real_management_workflow` 接续实际头 `0026_strengthen_health_baseline`。升级前SQLite备份位于忽略目录 `.runtime/pre-real-workflow-backups/`。迁移未包含自动比较发现的历史无关索引差异，也未修改原医疗模型语义。

标准 `scripts/build_portfolio_demo.py` 已接入 `scripts/seed_real_workflow_demo.py`：只建立一名合成入组会员，不通过脚本完成管理故事；重建演示库不会丢掉该入口。浏览器使用独立合成数据库，问卷、报告、确认、日志和执行均从真实Streamlit界面操作。

运行种子前明确设置已迁移的合成演示数据库，例如 `DATABASE_URL=sqlite:///./data/portfolio_demo.db`。不得将此演示命令指向真实PHI试点数据库。


## 交接补充

“继续 / 调整 / 稳定管理”保存复盘而不假装阶段已完成；负责人之后可明确确认进入已建立的下一阶段。原阶段的全部复盘字段保留在年度方案该阶段详情中。初评医学问题改变后必须重新取得对应医生确认；旧确认不能批准新问题。已确认的入组核对占位事项关闭，但不关闭真实疾病、风险或其他健康问题。日志时间按会员工作区本地时区显示。新会话继续问卷时进入首个未保存步骤。
