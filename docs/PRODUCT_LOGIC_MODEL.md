# Product Logic Model

实施前冻结于 `3ba46b2`。本轮不新增临床/Agent/设备能力，只整理读取、处理和记录关系。

## 三条主线与支撑层

1. **健康状态**：年度健康基线是确认冻结的起点；当前健康状态来自已确认有效记录。报告、数据、用药、问题、医疗事件与依据服务于解释变化，不是用户需要理解的系统对象。
2. **健康运营**：变化或人工请求进入待办。健管负责处理；必要时由医生判断；已确认决定通过计划、任务、服务执行。状态、负责人、期限、下一步在同一上下文出现。
3. **长期记录**：阶段结果是观察变化；时间轴只投影既有事实。历史复盘帮助人工决定下一周期，不由UI自动建立新计划或覆盖基线。
4. **支撑能力**：AI、Agent、知识、设备、导入、规则、集成、反馈、审计和Trace进入管理员。成员保留上传报告、数据来源及引用；健管保留自动跟进中的人工确认，技术配置不混入业务导航。

四层：角色 → 三条核心业务 → 报告/观测/用药/健康问题/医疗事件等事实 → 支撑服务。层是责任和信息组织，不是必须逐级点击的菜单。

## 共享投影与一致性

新增只读 `ProductProjectionService`，复用现有健康图表、基线、待办服务。选择当前计划采用执行中优先、其次暂停、再计划中；同状态按最新创建时间。没有当前计划时不能把历史完成计划标为进行中。

同一成员在成员页、360、医生上下文共用：当前计划、负责人、有效数据、待医生集合。每次页面运行新建投影，不跨会话缓存ORM，不在投影中写数据库。图表继续使用既有标准化投影与坐标轴。

统一队列仍以原责任记录为主，关联风险/任务/医生不重复建责任。现有待审批自动跟进与待医学确认基线补入只读队列；已有结果通过原随访任务进入执行，不把已归档结果再创建为待办。

状态字典按业务域解释枚举：年度基线CONFIRMED是“已确认”，医生CONFIRMED是“已完成”。同一对象跨页使用相同域，不将不同对象的同名枚举强行当同一状态。风险颜色和规则不改变。

## 写入命令核对

|操作|现有共同业务路径|本轮处理|
|---|---|---|
|报告确认|care_commands.confirm_report_candidate → ReportParsingService|两端共用原UI的确认、年度初稿、进度事件路径；API补齐原来缺失的初稿副作用；正式年度基线不覆盖|
|风险处理|RiskOperationsService|保留全部人工操作|
|医生完成|care_commands.complete_review|主页面与API已共用；旧兼容入口统一到该命令，避免漏发/重复发事件|
|计划建立/调整|care_commands.save_program → chronic_care|保留；API创建复用create_program，API当前没有独立调整路由，不伪称已有|
|任务完成|TaskTransitionService.complete|保留|
|服务完成|MemberServiceOperations原完成方法|两个UI入口保留同一服务；API当前无对应完成路由，不新增API|
|阶段结果|care_commands.record_outcome|保留；UI后续决定沿用apply_outcome_decision|

本轮不为表面统一添加并不存在的API，也不改医疗阈值、基线冻结、证据语义或医生责任。
